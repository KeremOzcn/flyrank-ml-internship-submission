FlyRank: checking a content refresh rule before building a model

Status: Task framing and baseline complete Dataset: 30,000 anonymized pages · 32 clients

The problem

A content team has more pages than it can review at once. Page age alone is an easy way to build a queue, but being old does not necessarily mean a page needs attention. The decision I framed was: which pages should an editor inspect first for a possible refresh?

What I did

I used FlyRank's starter dataset: 30,000 anonymized content pages across 32 clients. It contains search activity and freshness signals, but no record showing that a refresh helped. That limits what I can call a result.

I kept pages with at least 100 impressions over 90 days and a nonzero previous 30-day impression count — leaving 21,758 pages with enough visibility for a provisional screen. I used observed impression decline as a proxy for review relevance: the dataset labels a page "down" when impressions fell by more than 20% between two 30-day windows.

I separated the label from the working signals, documented that the remaining 90-day metrics overlap the decline window, and built a stale-first baseline before training any model.

What came of it

0.240 Baseline Precision@50
0.740 Random Forest Precision@50
0.542 Base rate (positive class)

The stale-first rule reached Precision@50 = 44.0% on my filtered slice — below the 60.4% random expectation. On the full pipeline with client-holdout validation (run by me, Sept 9 2026), the random forest reached Precision@50 = 0.740, a 3.1× lift over the baseline.

The deliverable is a reproducible framing notebook, a baseline to challenge, and a ranked review queue with reason codes. An editor still inspects each page before choosing whether to update facts, expand coverage, revise metadata, or leave it alone.

Limits

  • The trend window overlaps with the 90-day activity metrics — this is decision-support, not prospective prediction.
  • The proxy measures observed decline, not refresh need. A page may be declining for reasons a refresh cannot fix.
  • No held-out evaluation on a separately collected dataset has been performed.

How I work

Baseline before model

I build a transparent rule first — one a content team would naturally build without ML — and measure it on the same data and metric as the model. If the baseline is below base rate, the model has a clear job. If the baseline is already good, the model needs to justify its complexity.

Leak-hunting

I check every feature against the label definition. In this project, trend_direction and trend_pct define the label — including them as features would be direct leakage. I also split by client (not randomly) so the model can't memorize client-specific patterns.

Receipts beside claims

Every number in my report traces to a committed JSON file (outputs/model_results.json). Re-running python scripts/run_all.py from a fresh clone reproduces every metric. No headline is taken on faith.

Where AI helped

I used AI to draft boilerplate pandas code, generate docstrings, and pressure-test my framing. The analytical decisions, the interpretation, and the honest reporting of a baseline that lost to chance — those are mine. The prompt iteration log shows the actual back-and-forth.
