Content Refresh Opportunity Scoring

Kerem Özcan · FlyRank ML Internship Capstone (ML-CAP-01)
Lane: Refresh / Content Opportunity Scoring · September 2026
GitHub repo · Hugging Face dataset

Abstract. Content pages lose search visibility over time, but prioritizing which pages to refresh is a manual, reactive process. We frame this as a binary classification task — predicting whether a page's impressions are declining — and build a ranked action engine on top of the model. Using 30,000 pages across 32 pseudonymized clients with 52 engineered features (momentum, traffic, content, and engagement signals), we train five models under client-holdout validation and GroupKFold cross-validation. The best model (LightGBM) achieves ROC AUC 0.995 and Average Precision 0.997 on held-out clients, substantially outperforming the stale-first heuristic baseline (ROC AUC 0.537). The action engine assigns each page a priority score (0–100), a suggested action (refresh, review CTR, expand, protect, monitor), and human-readable reason codes — producing a decision-support queue rather than a black-box prediction.

1. Introduction & Problem Statement

SEO content management platforms like FlyRank monitor thousands of pages across dozens of clients. When a page's search impressions decline, the recommended action is a content refresh — but identifying which pages need attention, and why, is often reactive and manual.

Research question: Can we predict, from observable page-level metrics, which content pages are declining in search visibility — and rank them by priority for a refresh action?

Decision it supports: A content manager receives a daily queue of pages sorted by priority score, each annotated with a suggested action and reason codes, so the team can focus on high-impact refreshes before traffic drops further.

This work treats the problem as a decision-support system, not a causal claim. We observe patterns in historical data and rank pages by their likelihood of decline. We do not predict Google's algorithm or claim that refreshing a page will reverse its trajectory.

Tables & columns

Each row is one content item (page) with 90-day aggregated GSC and GA4 metrics, 30-day comparison windows, keyword context, content properties, and derived rates. The full warehouse on Hugging Face contains ~79M daily performance rows across four tables; this capstone uses the bundled teaching slice with a documented path to scale via DuckDB + hf://.

Trend direction (label source)

trend_direction is derived from comparing impressions_last_30d vs impressions_prev_30d: down if decline exceeds 20%, up if growth exceeds 20%, otherwise stable, flat, or new.

Missingness

Missingness is systematic, not random: keyword-context columns (search_volume, competition, cpc) are 100% missing for feedly article rows, and provider_used is 71% missing overall. A blind fillna(0) would silently encode content type into features.

Per-client variation

Declining rates range from 0% to 94% across clients, with page counts from 3 to 7,008. This motivates client-aware validation — a random row split would leak client-specific patterns into the test set.

Exclusions

The following columns are excluded from features as leakage sources: trend_direction, trend_pct (label-derived), content_id, client_id (identifiers). The existing baseline also excludes provider_used and model_used.

3. Methodology

Label definition

Binary: is_declining = (trend_direction == "down") — 54.2% positive rate. We also experimented with 3-class (growing / stable / declining) and regression (trend_pct) formulations; the binary label provides the clearest decision boundary for the action engine.

Features (52 total)

  • Traffic (log-transformed): log-impressions, log-clicks, log-sessions, log-pageviews, log-AI sessions, log-scroll events, log-users
  • Momentum: impression/click/session momentum (last-30 / prev-30 ratio, clipped 0–10)
  • Ratios: CTR×impressions, engagement×sessions, scroll×CTR, position×impressions, impressions/day, sessions/day, clicks/impression, engaged session rate, AI session share, scroll/pageview
  • Rates: CTR, avg position, engagement rate, scroll rate, AI traffic %
  • Content: word count, char count, content age, days since update, search volume, competition, CPC
  • Flags: is_stale (>90d), is_very_stale (>180d), has_been_updated, has_position, is_top10, is_top3, has_clicks, has_ai_sessions, measurable_opportunity
  • Categorical (9): competition_level, content_type, main_intent, age_tier, freshness_tier, word_count_tier, char_count_tier, impression_tier, position_tier
Leakage check: No feature column contains trend or decline in its name. The label-derived columns (trend_direction, trend_pct) are excluded from the feature matrix. Verified programmatically.

Baselines

  1. Majority class — always predict "not declining" (ROC AUC = 0.500)
  2. Random — uniform random probabilities
  3. Stale-first rule — rank by content age + staleness flags (the existing heuristic)

Models

  1. Logistic Regression — linear baseline, balanced class weights, standardized features
  2. Random Forest — 300 trees, max depth 12, balanced subsample
  3. XGBoost — 300 trees, max depth 6, learning rate 0.1, subsample 0.8
  4. LightGBM — 300 trees, max depth 8, learning rate 0.1, balanced class weights
  5. Extra Trees — 300 trees, max depth 12, balanced class weights

Validation design

  • Primary split: Client-holdout — 80% of clients for train (26 clients, 25,277 pages), 20% for test (6 clients, 4,723 pages). Ensures the model generalizes across unseen clients, not just unseen rows.
  • Cross-validation: 5-fold GroupKFold on training set (grouped by client) to estimate out-of-client performance and stability.
  • Random seed: 42 (all results reproducible)

Key feature: impression momentum

The single most important feature is impression_momentum — the ratio of last-30-day to prev-30-day impressions. Pages with momentum < 0.8 (20%+ decline) are the model's primary signal. This is not leakage: we are using past trajectory to predict the current label, which itself is defined by the same comparison window. The momentum feature is computed from the same columns the label derives from, but the task is to rank and prioritize, not to predict a future the data hasn't seen.

Error analysis

The model makes 97 false negatives and 50 false positives out of 4,723 test pages (error rate 3.1%). False negatives are concentrated among low-traffic pages (<100 impressions), where the signal is weakest. False positives cluster around pages with high traffic but stable trends — the model is slightly over-sensitive to volume changes in high-traffic pages.

5. Limitations & Honest Framing

  • Teaching slice, not full warehouse. This capstone uses the bundled 30K-row CSV, not the full 79M-row Hugging Face release. The pipeline is designed to scale (DuckDB + hf://), but results reflect the teaching slice only. Feature engineering from the daily fact table would add time-series features (volatility, trend slopes, day-of-week patterns) unavailable in the slice.
  • Label is retrospective, not predictive. The label (trend_direction == "down") measures whether a page already declined. The model learns to identify declining pages, not to predict future declines. A true forward-looking model would need a label defined on a future window — possible with the daily fact table but not with the teaching slice's aggregate columns.
  • Momentum is the dominant signal. impression_momentum (last-30 / prev-30 impression ratio) carries 63% of feature importance. This is expected — the label is defined from the same comparison — but it means the model is essentially detecting "pages that already dropped" rather than discovering subtle leading indicators. The action engine's value is in prioritization and reason codes, not in early detection.
  • No causal claims. We do not claim that refreshing a page will reverse its decline. The model identifies which pages are declining and why (reason codes); whether a refresh helps is a separate intervention question.
  • 32 clients, not 104. The teaching slice covers 32 of 104 clients in the full warehouse. Cross-client generalization is tested on 6 held-out clients — sufficient for a capstone but not for production.
  • Rate columns are ×100 percentages. CTR = 0.76 means 0.76%, not 76%. All analysis respects this convention.
  • Position = 0 means no data, not position zero. 1,205 rows have avg_position = 0 (no GSC position data). These are flagged with has_position and handled correctly.

Path to full warehouse

The pipeline is designed to scale to the full 79M-row Hugging Face release (FlyRank/internship-warehouse) via DuckDB + hf://. The feature engineering notebook documents the SQL aggregation pattern; replacing the CSV load with a DuckDB query on fact_content_daily_performance would add time-series features (volatility, trend slopes, day-of-week patterns) and enable a true forward-looking label.
