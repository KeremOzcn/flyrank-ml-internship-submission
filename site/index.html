Case Study

FlyRank: checking a content refresh rule before building a model

Status: Framing + baseline + model complete Dataset: 30,000 pages · 32 clients Split: Client-holdout Run: Sept 9, 2026

The problem

A content team has more pages than it can review at once. Page age alone is an easy way to build a queue, but being old does not necessarily mean a page needs attention. The decision I framed was: which pages should an editor inspect first for a possible refresh?

Unit of analysis: one content page. Output: a ranked review queue with priority scores and reason codes. Action: an editor inspects each page, then decides whether to update, expand, revise metadata, or leave it alone.

The data

FlyRank's starter dataset: 30,000 anonymized content pages across 32 pseudonymized clients. 44 columns of search activity and freshness signals. No client names, URLs, titles, or keywords.

Leakage guard: The label is_declining_label is defined as trend_direction == "down". The columns trend_direction and trend_pct are excluded from all features. Client IDs are used for the grouped split only — never as model input.

The baseline

Stale-first rule: sort by days_since_last_update descending, then by impressions_90d descending. The oldest, most-visible pages come first.

This is the rule a content team would build without ML. It's a fair comparison because it uses only signals available before any model, and it produces a total ordering evaluable at Precision@K.

Result: The stale-first rule reached Precision@50 = 0.240 on the client-holdout split — below the 0.542 base rate. Sorting by staleness + visibility is worse than random at finding declining pages.

The model

Random forest classifier, selected by Precision@50. 52 features: 18 numeric (log-transformed activity totals, content age, CTR, position, engagement) + 8 categorical (one-hot encoded: content type, intent, age tier, freshness tier, etc.).

Limits

  • The trend window overlaps with the 90-day activity metrics — this is decision-support, not prospective prediction.
  • The proxy measures observed decline, not refresh need. A page may be declining for reasons a refresh cannot fix.
  • No held-out evaluation on a separately collected dataset has been performed.

Methodology

How I work

Four habits that showed up in every decision on this project. They are not unique to ML — they are how I make sure a result I report is a result I can defend.

1. Baseline before model

I build a transparent rule first — one a content team would naturally build without ML — and measure it on the same data and metric as the model. If the baseline is below base rate, the model has a clear job. If the baseline is already good, the model needs to justify its complexity.

In this project, the stale-first baseline reached Precision@50 = 0.240 — below the 0.542 base rate. The model wasn't competing with a good rule. It was competing with a rule that's worse than flipping a coin.

2. Leak-hunting

I check every feature against the label definition. In this project, trend_direction and trend_pct define the label — including them as features would be direct leakage. I also split by client (not randomly) so the model can't memorize client-specific patterns and test on the same clients it trained on.

The split: client-holdout. 80% of clients (27,675 rows) for training, 20% (2,325 rows) for testing. No client appears in both sets.

3. Receipts beside claims

Every number in my report traces to a committed JSON file. Re-running python scripts/run_all.py from a fresh clone reproduces every metric. No headline is taken on faith.

4. Where AI helped

I used AI to draft boilerplate pandas code, generate docstrings, and pressure-test my framing. The analytical decisions — which baseline to build, which features to exclude, how to interpret a result that lost to chance — those are mine. The prompt iteration log shows the actual back-and-forth.

What I will not do: claim a result I did not measure. The original proof statement cited "~3× Precision@50" using the starter repo's reference numbers. I ran the pipeline myself, confirmed the same numbers, but rewrote the claim to lead with the baseline failure — because that's the finding that justifies the model, not the lift.
